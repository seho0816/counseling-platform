# AI 요약 JSON 응답 구조 (7번)

## 1. 응답 형식 (3항목 기준, 현재 프롬프트 v2)

```json
{
  "chief_complaint": "내담자가 호소하거나 보고한 어려움과 상태",
  "intervention": "기록에 적힌 상담자의 활동",
  "next_plan": "다음 회기 계획, 과제, 이후 일정과 안내"
}
```

| 필드 | 한글 이름 | 타입 | 규칙 |
| --- | --- | --- | --- |
| chief_complaint | 주요 호소 | 문자열 | 1~3문장, 비워 둘 수 없음 |
| intervention | 개입 내용 | 문자열 | 1~3문장, 비워 둘 수 없음 |
| next_plan | 다음 계획 | 문자열 | 1~3문장, 비워 둘 수 없음 |

- 기록에 해당 내용이 없으면 값은 정확히 `"기록에 없음"`이다. 빈 문자열이나 null을 쓰지 않는다.
- 위의 3개 외의 필드는 받지 않는다. 있으면 무시한다.

## 2. 팀 요구사항(4항목)으로 늘릴 때

팀 요구사항 정의서 FR-REC-04는 주호소, 상담 내용, 내담자 상태, 다음 계획 4항목이다. 4항목으로 정하면 필드를 아래처럼 맞춘다.

| 팀 항목 | 필드 이름 | 현재 3항목과의 관계 |
| --- | --- | --- |
| 주호소 | chief_complaint | 그대로 |
| 상담 내용 | intervention | 이름만 바뀜 (개입 내용) |
| 내담자 상태 | client_state | **새로 추가** (예: 수면, 기분, 일상 기능 등 기록에 적힌 상태) |
| 다음 계획 | next_plan | 그대로 |

4항목 프롬프트는 `7_요약_프롬프트_v2_4항목`에 준비해 두었다. 어느 쪽으로 할지는 팀 합의(13번)로 정한다.

## 3. 백엔드가 응답을 받을 때 검증하는 순서

1. 응답 문자열이 JSON으로 읽히는가. (코드 블록 표시 ``` 가 붙어 있으면 제거한 뒤 읽는다)
2. 필수 필드가 모두 있고 값이 비어 있지 않은 문자열인가.
3. 위를 통과하면 화면에 **"AI 생성 결과, 오류 가능성 있음"** 표시와 함께 상담자에게 보여 준다. 상담자가 확인·수정·승인하기 전에는 저장하지 않는다 (FR-SAF-03, FR-REC-05).

## 4. 실패했을 때 처리 (NFR-06)

| 상황 | 처리 |
| --- | --- |
| JSON을 읽을 수 없음 | 같은 요청을 1회 재시도 |
| 필드 누락 또는 빈 값 | 같은 요청을 1회 재시도 |
| 재시도도 실패 | 오류 안내를 보여 주고 상담자가 직접 요약을 입력하는 화면을 제공 |
| API 호출 자체가 실패(네트워크, 한도) | 오류 안내와 재시도 버튼, 수동 입력 경로 제공 |

## 5. 관측 결과 (Gemini gemini-3.5-flash-lite, 가상 기록 13건)

- 13건 모두 JSON 형식이 정상이었고 필드 누락이 없었다 (프롬프트 v1 기준).
- 같은 10건(30칸)을 프롬프트 v1, v2, v3로 돌려 6번 정답과 항목별로 대조했다.
  - 일치: v1 15칸, v2 18칸, **v3 23칸**
  - 원본에 없는 표현: v1 5칸, v2 1칸, v3 1칸
  - 10건 모두 JSON·필드 정상 (v1, v2, v3 공통)
- 최종 사용 프롬프트는 `7_요약_프롬프트_v3`(3항목)이다. 4항목으로 정하면 `7_요약_프롬프트_v3_4항목`을 쓴다 (4항목 버전은 호출 테스트를 하지 않았다).
- 남은 한계: 위기 신호 없음이 호소 칸에 들어가는 경우(SE04), '안내함' 같은 상담자 행동 표현이 가끔 들어가는 경우(SE20)가 있다. 상담자 검토 단계(FR-REC-05)로 걸러야 한다.
